# ADR-001: Контекст проекта

## Статус
Принято и реализовано.

## Контекст
Команда из четырёх человек, курс «Архитектура и проектирование
веб-приложений» . Выбранная тема —
сервис-генератор судоку с гарантией единственного решения: пользователь
задаёт параметры, ядро генерирует и/или решает головоломку.

Стек фиксирован для стартового проекта курса (AGENTS.md): Python,
Django, Django Ninja, pydantic, pytest, ruff. Ключевое архитектурное
ограничение — вычислительное ядро (`core/`) не должно зависеть от
Django, БД и HTTP.

## Решение
Единый контракт на два входа: `core.schemas.SudokuParams` (`mode`,
`grid`, `difficulty`, `seed`) используют одновременно `web/forms.py`
(страница для человека) и `web/api.py` (Django Ninja, для программы) —
поля не дублируются в двух местах с риском разойтись по именам.

`core/` (`solver.py`, `schemas.py`) не содержит ни одного импорта Django
— проверено: тесты в `core/tests/` запускаются без поднятого Django
и без базы данных. Побочные эффекты (сохранение в БД, HTTP-ответы,
статус фоновой задачи) — только в `web/services.py`.

## Последствия
- Новое поле входа — правка в одном месте (`core/schemas.py`), форма и
  API получают его синхронно.
- Ядро тестируется в изоляции — `pytest core/tests/` не требует
  `DJANGO_SETTINGS_MODULE` и БД (в отличие от `tests/test_api.py`, где
  нужен `pytest-django`).

## Рассмотренные варианты (дополнено 02.10, пара 16)

Стек (Python, Django, Django Ninja, pydantic) задан стартером курса — это
условие, а не наш выбор. Выбирали мы другое: где провести границу ядра и где
проверять вход.

| Вариант | Что это дало бы | Почему нет |
|---|---|---|
| Расчёт прямо во view и в функции API | меньше файлов | один алгоритм в двух местах; тест алгоритма требует Django и HTTP; из консоли не запустить |
| Проверка входа в форме Django, а в API — своя | привычно для Django | два набора правил: исправили одно — забыли другое; повтор цифры в строке пришлось бы проверять дважды |
| Схема в `web/` (рядом с API) | всё про вход в одном пакете | ядро зависело бы от веб-слоя: консольный запуск тянул бы Django |
| **Схема pydantic в `core/`, одна на форму и API** — выбрано | правила в одном месте; ядро работает без сайта | см. ниже |

## Последствия, которых не было в первой версии (дополнено 02.10)

- **Поля формы объявлены второй раз.** `web/forms.py` перечисляет те же
  четыре поля руками. Фраза «поля не дублируются» выше верна для правил
  проверки (они только в `core/schemas.py`, форма передаёт данные в
  `SudokuParams` — `web/views.py:54–59`), но не для списка полей: новое поле
  надо добавить и в схему, и в форму. Совпадение имён держится на нас.
- **Граница подтверждена запуском.** С пары 16 ядро запускается из консоли:
  `python -m core сетка.txt` (`core/__main__.py`). Тест
  `core/tests/test_cli.py::test_runs_as_module_without_django` проверяет, что
  Django при этом не загружен.
- **В модели осталось лишнее.** `Task.Kind.VALIDATE` объявлен
  (`web/models.py:14`), а схема принимает только `solve` и `generate`
  (`core/schemas.py:23`). Модель и договор входа разошлись — цена того, что
  они живут в разных слоях и никто не сверяет их автоматически.
