## 1. DEBUG
Проверил: Ташлигов Ахмед.
Где: `sudoku_service/settings.py:13` (было) — `DEBUG` по умолчанию `"True"`;
в `.env.example:2` тоже `True`.
Как воспроизвести: запустить без `.env`, открыть несуществующий адрес
`/nesush/` → жёлтая страница Django со списком всех адресов сайта
(`admin/`, `api/`, …) — готовая карта для перебора; на падающем адресе —

выключен, включается только явно (`DJANGO_DEBUG=1` в своём `.env`).

адресов сайта 0; при `DJANGO_DEBUG=1` — список адресов есть.
«Если оставить DEBUG=True на сервере», любой посторонний по первой же
ошибке или опечатке в адресе видит устройство сайта: адреса, код, пути,
настройки.

## 2. SECRET_KEY
Проверил: Ташлигов Ахмед.
Где: `sudoku_service/settings.py:12` (было) — запасной ключ прямо в коде:
`os.environ.get("DJANGO_SECRET_KEY", "insecure-dev-key-change-me")`. Код
лежит на GitHub — ключ знает любой.
Как воспроизвести: запустить без `.env` — сервер стартует с ключом из кода.
Этим ключом подписаны cookie входа: зная его, можно подписать cookie
«вошёл: администратор», и сервер поверит.
Исправлено: да — `sudoku_service/settings.py:18–27` (образец — слайд 27):
ключ только из окружения; без ключа и с выключенным DEBUG —
`RuntimeError("задайте DJANGO_SECRET_KEY …")`, сервер не стартует.
Запасной `dev-only-key` — только когда DEBUG включён руками. В
`.env.example` — команда генерации ключа, сам ключ не хранится.
Проверка: `python manage.py check` без `.env` → «задайте DJANGO_SECRET_KEY»;
с `.env` (`DJANGO_DEBUG=1`) → работает. Тесты
`test_server_refuses_to_start_without_secret_key`,
`test_dev_mode_starts_without_secret_key`.

## 4. Границы входа
Проверил: Байраев Магомед-Эми (ядро и схема), Ташлигов Ахмед (API).

**4а. «Решить» без сетки.**
Где: было — `POST {"mode": "solve"}` → `202`, задача создавалась, ошибка
появлялась потом в фоне (`web/services.py:45–46`).
Как воспроизвести: `POST /api/tasks` с `{"name": "x", "params": {"mode": "solve"}}`.
Исправлено: да — `core/schemas.py:31–39`, `model_validator`: сочетание
`mode=solve` + нет `grid` → ошибка → `422` сразу, задача не создаётся (на
форме — ошибка под сеткой). Тесты `test_solve_without_grid_is_422_and_no_task`,
`test_form_solve_without_grid_shows_error_and_no_task`.

**4б. Сетка без решения — перебор без предела.**
Где: `core/solver.py` — `limit=2` ограничивал число решений, а не шагов.
Как воспроизвести: решить сетку Норвига
`.....5.8....6.1.43..........1.5........1.6...3.......553.....61........4.........`
— повторов нет, схема её пропускает; перебор шёл больше 150 с (наш замер:
2 000 000 шагов за 108 с, не закончил). Один такой запрос занимает сервер.
Исправлено: да — `core/solver.py:23`, `MAX_STEPS = 50_000`, по замеру:
классическая сетка — 52 шага, «самая сложная» Инкалы — 18 936 (≈1.4 с),
худший вызов при генерации hard — 1 275. Предел в 2.6 раза выше Инкалы.
Превышен → `"too complex"` → статус «Ошибка: превышен предел перебора»
через ~3–4 с (вживую: 4.2 с), а не 150+. Перебор кандидатов стал
детерминированным (`sorted`), иначе число шагов менялось бы от запуска к
запуску. Генератор такой результат тоже считает «не единственно»
(`core/generator.py`). Тесты: `core/tests/test_limits.py`,
`test_grid_without_solution_ends_with_error_not_hang`.

**4в. Длина имени задачи.**
Где: было — `web/api.py:15`, `name: str` без длины. В модели
`max_length=100`, но SQLite длину не проверяет.
Как воспроизвести: `POST` с `name` из 100 000 символов → `202` и в базе
целиком.
Исправлено: да — `web/api.py:21`, `Field(max_length=100)` → `422` с полем
`name`. Тест `test_long_name_is_422`.

**4г. seed.** На время расчёта не влияет, но верхней границы не было.
Исправлено: `core/schemas.py:29`, `0 ≤ seed ≤ 2³²−1`. Тест `test_seed_has_bounds`.

**Не сделано — план: частота запросов.** Сто запросов в секунду от одного
пользователя сейчас не ограничены; каждый — отдельный поток. План:
ограничение частоты на `POST /api/tasks` и форму (не больше N задач в
минуту на пользователя, ответ `429`) — вместе с переходом с потоков на
очередь задач.

## 7. CSRF и SQL
Проверил: Умаров Зелим.
CSRF: в каждой форме `method="post"` есть `{% csrf_token %}` — проверено по
всем шаблонам (форма задачи, вход, выход). API: на 30.09 токен не
проверялся («форма ок, API нет»); с пары 13 API работает через
`django_auth`, а он для `POST` сам проверяет CSRF-токен. Как воспроизвести:
вошедший пользователь, `POST /api/tasks` без заголовка `X-CSRFToken` →
`403 CSRF check Failed`, задача не создана (вживую и тест
`test_post_without_csrf_token_is_rejected`; форма без токена — тоже `403`).
SQL: искали `.raw(`, `.extra(`, `cursor.execute` — не найдено; все запросы
через ORM Django, значения передаются отдельно от запроса.
