# Sudoku Service

Веб-сервис-генератор судоку с гарантией единственного решения. Формат сетки
— строка из 81 символа (`1`-`9` и `.` для пустой клетки). Один контракт на
два входа: страница (для человека) и `/api/tasks` (для программы).

## Идея

Подробно, с обоснованием архитектуры («рамка») — в `docs/idea.md`.

## API

`POST /api/tasks` — `{"name": "...", "params": {"mode": "solve"|"generate", "grid": "...", "difficulty": "...", "seed": ...}}` → `202` + `{"id": ...}`.
`GET /api/tasks/{id}` — статус (`queued`/`running`/`done`/`error`).
`GET /api/tasks/{id}/result` — результат, когда `status == done`.
Полная документация с примерами запросов — `docs/api.md`; интерактивно —
`/api/docs` (Swagger, автогенерация Django Ninja).

## Структура проекта

- `core/` — вычислительное ядро. Не импортирует Django, не ходит в БД и HTTP.
  - `core/solver.py` — решатель (backtracking + MRV).
  - `core/generator.py` — генератор головоломок: строит полную сетку,
    удаляет клетки по одной, после каждого удаления проверяет
    единственность решения через `solve()` (limit=2); при фиксированном
    `seed` результат воспроизводим.
  - `core/schemas.py` — `SudokuParams`: pydantic-валидация входа ДО расчёта
    (длина, допустимые символы, паттерны mode/difficulty, отсутствие дублей
    в строках/столбцах/блоках).
  - `core/tests/` — 16 тестов на чистую логику (эталоны + схема + генератор).
- `web/` — Django-слой:
  - `web/models.py` — `Task` (заявка, с полями `name`/`kind`/`status`/`params`/`error`), `PuzzleResult`.
  - `web/services.py` — единственная точка входа для views/API в `core/`; фон — поток, статус пишет прямо в `Task.status`; время расчёта — реальное, через `time.perf_counter()`.
  - `web/api.py` — тонкий Django Ninja роутер, почти не меняется.
  - `web/forms.py` — форма с теми же именами полей, что в `core/schemas.py`.
  - `web/views.py` — `index` принимает `POST`, создаёт задачу и
    перенаправляет на `task_detail`; `task_detail` показывает статус,
    результат или ошибку.
  - `web/templates/` — страница с формой (`index.html`) и страница
    результата (`task_detail.html`, автообновление, пока задача считается).
- `tests/test_api.py` — тест уровня API (нужен Django, поэтому отдельно от `core/tests/`).
- `tests/test_site.py` — путь через сайт: форма → редирект → задача `done` с известным
  решением и `elapsed_ms > 0`; некорректная сетка не создаёт задачу.
- `docs/` — идея (`idea.md`), API-контракт (`api.md`), ER-схема
  (`ER.png`), архитектурные решения (`ADR-001.md`, `ADR-002.md`),
  самопроверка архитектуры (`fat_review.md`).

## Реперная точка 21.09

Требование чекпоинта: путь «форма → расчёт → результат» должен работать
целиком, время расчёта — настоящее, а не заглушка, и должен быть
содержательный следующий шаг (генератор с проверкой единственности).

- **Вход:** опубликованная головоломка судоку, 81 символ,
  `53..7....6..195....98....6.8...6...34..8.3..17...2...6.6....28....419..5....8..79`
  (классический пример, широко публикуется вместе с решением, в т.ч. на
  Wikipedia).
- **Ожидаемый выход:** единственное решение
  `534678912672195348198342567859761423426853791713924856961537284287419635345286179`.
- **Откуда известен ответ:** решение опубликовано вместе с условием
  независимо от нашего кода — мы не генерировали пару вопрос/ответ сами
  (см. также `core/tests/test_reference_puzzle.py` — вторая, более сложная
  эталонная головоломка, Arto Inkala, 2012, с ответом, сверенным по
  независимому источнику).
- **Алгоритм:** `core/solver.py` — backtracking с MRV-эвристикой
  (наименее заполненная клетка выбирается первой), поиск до двух решений
  (`limit=2`) для проверки единственности без лишнего перебора.
- **Генератор (следующий шаг, реализован):** `core/generator.py` строит
  полную валидную сетку, затем удаляет клетки по одной в порядке,
  зависящем от `seed`; после каждого удаления проверяет единственность
  тем же `solve()` и откатывает удаление, если решений стало больше
  одного. Эталон для генератора — `core/tests/test_generator.py`:
  фиксированный `seed=42`, тест проверяет и воспроизводимость (тот же
  seed → тот же результат, в том числе в разных процессах — как после
  рестарта сервера), и единственность решения.
- **Ограничение текущей версии:** нет защиты от параллельной записи при
  нескольких одновременных задачах (SQLite + threading, см. ADR-002);
  генератор не гарантирует ровно фиксированное число подсказок для
  каждой сложности (только не больше целевого — если разрежение
  останавливается раньше из-за потери единственности, подсказок может
  быть немного больше цели).

## Замер производительности (пара 11)

`elapsed_ms` пишется в базу самим расчётом (`web/services.py`, обёрнуто в
`time.perf_counter()` — см. «Реперная точка 21.09» выше), поэтому замер —
не отдельный бенчмарк-скрипт, а те же самые значения, что видит
пользователь на странице результата и в `/admin/web/puzzleresult/`. По 10
запросов на каждый вход, через реальный `POST /api/tasks`:

| Вход | Среднее время | Наибольшее время |
|---|---|---|
| Лёгкая сетка (генератор, `difficulty=easy`, 40 подсказок) | 2.77 мс | 3.98 мс |
| Классическая (Wikipedia, 30 подсказок) | 3.75 мс | 5.30 мс |
| «Самая сложная в мире» (Arto Inkala, 21 подсказка) | 1769.71 мс | 1990.21 мс |
| Генерация, `difficulty=hard` (10 разных `seed`) | 292.92 мс | 564.80 мс |

Разница между 30 и 21 подсказкой — не пропорциональная: у Инкалы решение
почти в 500 раз дольше, чем у классической сетки, хотя подсказок меньше
всего на 9. Чем меньше заполнена сетка, тем позже MRV-эвристика находит
клетки с малым числом кандидатов, и тем больше тупиков перебору
приходится откатывать. Именно эта нелинейность и есть причина, по
которой `mode=solve`/`mode=generate` считаются асинхронно (`202` +
опрос статуса), а не отдаются синхронным ответом.

## Пара 13: вход и «только свои задачи»

До пары 13 сервер не спрашивал, кто пришёл: любой, даже без входа,
открывал чужую задачу по номеру (проверено преподавателем 30.09 — аноним
получал `200`). Теперь — три шага, каждый в своём слое (подробно и с
обоснованием — `docs/ADR-003.md`):

1. **Владелец** — `web/models.py`: поле `Task.owner` (ссылка на
   пользователя Django), миграция `web/migrations/0003_task_owner.py`.
   Старые задачи остаются без владельца (`null=True`), миграция на
   существующей базе не падает — проверено.
2. **Вход** — `/accounts/login/` и `/accounts/logout/` (готовые страницы
   Django), шаблон `web/templates/registration/login.html`,
   `@login_required` на странице формы и странице задачи. Весь API —
   `auth=django_auth` (та же cookie, что у сайта).
3. **Фильтр** — `web/services.py::get_task(user, task_id)`:
   `Task.objects.filter(id=task_id, owner=user)`. Одно место для страницы
   и API. Чужая задача → `None` → `404`, как несуществующая.

| Кто | `/` | `/tasks/1/` | `/api/tasks/1`, `/api/tasks/1/result` | `POST /api/tasks` |
|---|---|---|---|---|
| Аноним | `302` → `/accounts/login/` | `302` → вход | `401` | `401` (из `/api/docs`) |
| Пользователь 1 (владелец) | `200` | `200` | `200` | `202` |
| Пользователь 2 (чужой) | `200` | **`404`** | **`404`** | `202` (своя задача) |

Проверено вживую на сервере (два пользователя, два набора cookie, вход
через настоящую форму с CSRF-токеном) и тестом `tests/test_access.py`.
Если убрать `owner=` из фильтра в `services.get_task`, тест падает с
`assert 200 == 404` — Пользователь 2 снова видит чужую задачу.

**Как проверить самому:** `python manage.py createsuperuser` — первый
пользователь; второго завести в `/admin/` → «Пользователи» → «Добавить».
Обычное окно — вход Пользователем 1, решить сетку, запомнить номер
задачи. Окно инкогнито — `/` перебрасывает на вход; войти Пользователем
2 и открыть `/tasks/<номер>/` → `404`.

Тесты: `pytest` — 27, все зелёные (22 прежних + 5 новых: 3 в
`tests/test_access.py`, аноним в API → `401`, аноним на сайте → вход).
Старые тесты сайта и API переведены на вошедшего пользователя (фикстура
`auth_client` в `tests/conftest.py`) — без входа они теперь честно
получают `302`/`401`.

## Пара 14: проверка безопасности

Восемь пунктов проверки — `docs/security_review.md` (где, как воспроизвести,
исправлено или план). Что исправлено:

| Находка (проверка 30.09) | Было | Стало |
|---|---|---|
| «Решить» без сетки | `202`, ошибка потом в фоне | `422` сразу, задача не создаётся (`model_validator` в `core/schemas.py`) |
| Сетка без решения | перебор > 150 с, предела нет | предел 50 000 шагов (по замеру: Инкала — 18 936) → через ~4 с статус «ошибка: превышен предел перебора» |
| Длина `name` | 100 000 символов → `202` и в базе | `Field(max_length=100)` → `422` |
| `DEBUG` | по умолчанию включён | по умолчанию выключен, включается в своём `.env` (`DJANGO_DEBUG=1`) |
| `SECRET_KEY` | запасной ключ в коде | только из окружения; без ключа и без DEBUG сервер не стартует |
| Версии | ни одного `==` | закреплены `pip freeze`; `pip-audit` — уязвимостей нет |

Без находок: лишнее в git, XSS (`|safe` нет), SQL (запросов строкой нет),
CSRF (токен во всех формах, API проверяет его с пары 13). Открыто:
ограничение частоты запросов — план в `docs/security_review.md`.

**Важно после обновления:** `.env` теперь обязателен (и для сервера, и для
`pytest`): `cp .env.example .env`. Без него `python manage.py check`
честно скажет «задайте DJANGO_SECRET_KEY». Старые `.env` с
`DJANGO_DEBUG=True` продолжают работать.

**Интерфейс.** Сетка 9×9 вместо строки из 81 символа: ввод по клеткам
(стрелки, Backspace, вставка строки целиком), подсветка повторов сразу при
вводе, примеры (классическая, Инкала, сетка без решения). На странице
задачи — подсказки «печатным» шрифтом, найденные цифры — «карандашом»;
статус «Считается…» обновляется сам. На главной — «Мои задачи» (только
свои). Стили встроены в шаблоны: при выключенном DEBUG `runserver` не
отдаёт статику, а страница должна выглядеть одинаково.

Тесты: `pytest` — 42 (было 27): `tests/test_security.py` — 8,
`core/tests/test_limits.py` — 6, список «Мои задачи» в
`tests/test_access.py` — 1. Каждое исправление проверено и обратно: откат
исправления → соответствующий тест краснеет.

## Пара 15: тесты без потока и CI

![tests](https://github.com/whYmar0/azaza-web/actions/workflows/tests.yml/badge.svg)

**Почему тест падал.** `tests/test_site.py` иногда падал (у преподавателя
30.09 — 3 из 8; у нас воспроизвелось 1 из 8 и ещё раз 1 из 4). В логе:
`database table is locked: web_task`. Тестовая база SQLite одна на тест и
фоновый поток: тест и поток лезли в неё одновременно, поток получал
«таблица занята» и умирал, задача навсегда оставалась `queued`, и тест через
10 секунд падал на «Задача зависла».

**Что поменяли** (образец — слайд 69):

- `web/services.py:33–36` — `if getattr(settings, "RUN_IN_THREAD", True)`:
  обычно расчёт в фоновом потоке, как раньше; иначе — `_run(...)` сразу, в
  том же потоке. В `sudoku_service/settings.py` — `RUN_IN_THREAD = True`.
- `tests/conftest.py:20` — фикстура `autouse=True` ставит
  `settings.RUN_IN_THREAD = False` для всех тестов сайта и API. Задача уже
  «готово» к первому опросу; `_wait_until_finished` в `test_site.py` не
  трогали.
- Новый тест задачи `tests/test_api.py::test_create_task_returns_202_and_id_then_result`:
  отправили задачу → `202` и номер → статус `done` → `/result` = `200` с
  опубликованным решением.
- Обратная проверка `test_normal_mode_still_uses_background_thread`: при
  `RUN_IN_THREAD = True` запрос не считает сам, а запускает поток и сразу
  отвечает `202` (задача ещё `queued`). Без этого теста поток можно было бы
  случайно выключить везде — и ни один тест бы не заметил.
- `.github/workflows/tests.yml` — робот GitHub Actions (слайд 48): после
  каждого `push` чистая машина, Python 3.12, `pip install -r
  requirements.txt` и `-r requirements-dev.txt` (pytest — там), `pytest -q`.
  Плюс `DJANGO_DEBUG: "1"`: с пары 14 без ключа и без DEBUG проект не
  стартует — без этой строки первый прогон был бы красным с «задайте
  DJANGO_SECRET_KEY».
- «23 подсказки» → «21» у Инкалы (`core/tests/test_reference_puzzle.py:8`,
  README в разделе замеров) — посчитано по самой сетке.

**Что получилось.** `pytest -q` 10 раз подряд — 10 раз 44 зелёных;
`test_site.py` отдельно 25 раз подряд — ни одного падения (до исправления —
1 из 8). Шаги робота повторены вручную на Python 3.12 в чистой копии без
`.env`: без `DJANGO_DEBUG` — красный с понятной причиной, с ним — 44
зелёных. Вкладка Actions — после пуша.

## Пара 16: ядро из консоли и архитектурный документ

**Ядро из консоли** (требование сдачи 28.09) — `core/__main__.py`:

```bash
python -m core сетка.txt
```

В `сетка.txt` (лежит в корне репозитория) — головоломка Википедии из теста,
девятью строками по девять символов. Ответ — опубликованное решение:
`534678912672195348198342567859761423426853791713924856961537284287419635345286179`.

Сайт для этого не нужен: ни Django, ни базы, ни `.env`. Путь тот же, что у
сайта и API: сначала схема (`core/schemas.py`), потом `solve()`. Вместо
падения — причина словами и код выхода:

| Что в файле | Что напечатает | Код выхода |
|---|---|---|
| сетка с единственным решением | решение, 81 цифра | 0 |
| 80 символов, чужой символ, повтор цифры | «Ошибка во входе: …» | 1 |
| пустая сетка | «Решение не найдено: решений больше одного» | 1 |
| сетка без решения (Норвиг) | «Решение не найдено: превышен предел перебора (50000 шагов)…», около 3 с | 1 |
| файла нет или аргументов не один | «Не удалось прочитать файл» / «Использование: …» | 2 |

Тесты — `core/tests/test_cli.py` (8). Последний запускает ядро отдельным
процессом и проверяет, что Django при этом не загружен.

**Архитектурный документ** — `docs/architecture.md`, 12 разделов по шаблону
стартера, под каждым — автор. Шесть диаграмм (контекст, контейнеры, слои,
модель данных, состояния задачи, развёртывание) — Mermaid, GitHub рисует их

Тесты: `pytest` — 52 (было 44), из них 30 — ядро, без Django и базы.

## Запуск с чистой машины

```bash
git clone <url> sudoku-service && cd sudoku-service
python -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\Activate.ps1
pip install -r requirements.txt -r requirements-dev.txt
cp .env.example .env
python manage.py migrate
python manage.py createsuperuser
python manage.py runserver
```

Тесты: `pytest`. Админка: `http://127.0.0.1:8000/admin/`. API-документация:
`http://127.0.0.1:8000/api/docs`.

## Архитектурные принципы

1. `core/` не зависит от Django, БД и HTTP.
2. Views и API не содержат бизнес-логики — только вызывают `web/services.py`.
3. Вход валидируется pydantic-схемой до расчёта. Никакого `eval`.
4. Секреты — только в `.env`.
